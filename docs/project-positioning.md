# 项目定位与 Agent 协作（Project Positioning and Agent Collaboration）

## 动机与优先级（Motivation and Priorities）

GlassMachine 首先是一个兴趣驱动的项目：出于对计算机制的好奇，构建自己想要的、从 Bit 到 Attention 的可执行计算系统实验室。利用 AI 把真正想做的事情变成现实，是项目的核心实践；复杂度是需要解决的问题，不是追求的指标。

项目同时作为作者从算法背景转向 AI／LLM PM 的作品之一。优先级为：

1. 实现真实的探索与学习目标，持续完成可验证的成果。
2. 在建设过程中提升借助 AI 拆解、执行、判断、纠偏和交付的能力，形成有证据的产品思考。
3. 逐步让成果服务于有相似需求的人，降低运行、理解和分享的门槛。

推广具有价值，但不是当前第一优先级。项目不以商业化、增长或创业为默认目标，不为求职叙事额外堆叠功能；路线可以随学习目标、实现证据和使用反馈调整，重要变化按既有工程约定记录。个人需求是起点；他人是否共享该需求，需要后续证据。

## 职业目标与作品价值（Career Direction and Portfolio Value）

目标方向是类似 Codex、WorkBuddy 所代表的 Agent／开发者效率产品：释放大模型能力，帮助人们完成过去因知识、时间、精力或执行阻力而难以推进的事情。此处描述的是职业兴趣，不评价这些产品的具体能力或招聘要求。

GlassMachine 与这一方向有两层关联：

- **交付成果**：把抽象的计算机制变成可运行、可观察、可验证的学习实验。
- **建设过程**：作为 AI 工具的真实长期用户，实践从想法、任务拆解到实现、验证、恢复与交付的完整流程。

第二层与目标岗位直接相关。作品需要展示目标选择、优先级、技术取舍、人机分工、失败恢复和结果证据；仅有代码规模、复杂架构或使用次数不足以证明产品判断。

作者的算法背景有助于独立验证和技术判断，也会掩盖普通用户的困难。复盘有代表性的专业经验介入时，可以考虑：缺少这段经验的用户会怎样，工具可以提供什么支持？个人经验可以产生产品假设，不能直接代表所有用户。

## 教育定位与边界（Educational Positioning and Boundaries）

项目可作为 AI for Education 的实践 demo，当前准确表达是“借助 AI 构建的交互式计算系统学习实验室”。它希望让学习者通过修改、运行和追踪实验理解计算机制。

AI 参与开发、AI 直接辅助学习、学习效果得到验证，是三个不同的结论。AI 导师、自然语言实验设计和基于轨迹的解释是可探索方向，不能描述为现有能力，也不应为了突出 AI 身份而默认加入。

产品思维体现为关注学习者想完成什么、如何进入实验、在哪里卡住、怎样判断理解；不要求立刻开展商业化或用户增长。每个适合展示的里程碑应形成一个小而完整的体验，并继续服务于整体系统。

例如，M1 全加器可围绕“预测结果—修改输入—观察传播—解释进位—用新输入检验理解”设计体验。这是建议的验收场景，不表示相关功能已经完成，不改变既有 M1 范围。

## 任务推进方式（Agent Execution Workflow）

更高阶地使用 Agent，意味着在可理解、可验证的前提下，让它承担完整任务，减少人必须逐步推动的环节。自主运行时长、Agent 数量和生成代码量不作为目标。

对重要任务采用以下轻量流程；简单修改不需要完整模板或额外文档：

1. **明确任务契约**：目标、学习或使用场景、范围与不做事项、依赖、验收依据。以既有规格与里程碑为起点，需要调整时说明依据与影响。
2. **完成闭环**：在授权范围内调查、实现、测试、检查差异并交付；遇到关键歧义或权限边界时向人寻求判断。
3. **依据证据恢复**：失败后定位首个分歧，检查假设并调整策略；避免无诊断地重复执行。区分缺少信息、工具限制、实现缺陷和目标不清。
4. **保留可接续状态**：在现有任务记录中留下完成项、未解决问题、验证结果和下一步，使恢复工作不依赖某次长对话。
5. **按需要分工**：独立评审、公开入口体验或可分离调查有明确收益时，可安排独立 Agent；说明输入、输出和责任边界，评估协调与返工成本。单 Agent 足够时不增加编排。

这一流程不扩大外部操作权限，不要求每次启动多个 Agent，也不改变工程正确性标准。Agent 评审不能替代独立参考模型和测试。

## 执行历史与决策证据（History and Decision Evidence）

Git 历史、diff、测试和已有 issue／PR 是执行证据的底座，不另建重复流水账。重要节点补充 Git 通常不能解释的信息：为什么作出选择、Agent 在哪里失败、人提供了什么判断、修正后的证据是什么。

记录按职责归位：体系结构和语义变化进入 ADR／规格；验收结果进入验证或里程碑文档；AI 协作经验优先附在现有任务、issue 或 PR 中。没有对应记录且经验值得复用时，再保存一份简短案例文档。无需保存完整聊天记录。

可使用以下案例结构：

```text
目标与完成标准：
代码基线／关联提交／任务：
Agent 承担的工作与实际工具、上下文条件：
阻塞或失败及证据：
人的关键判断与方案取舍：
最终变更、验证结果和剩余边界：
对工具或协作方式的改进假设、下一次验证方法：
```

历史缺陷可以作为案例候选，但不能仅凭提交历史推断是谁发现问题、谁作出判断或 AI 节省了多少时间。只记录能追溯的事实；未知项明确留空或标为未记录。

## Agent 体验与评估（Agent Experience and Evaluation）

缺少现实用户时，可以让 Agent 实际体验项目，发现安装、文档、任务流程和解释中的障碍。它提供早期评估，不等同于真实用户研究。

| 方法 | 可提供的证据 | 不能直接证明 |
| --- | --- | --- |
| 从干净环境安装、执行公开示例 | 指定环境下是否能完成任务，缺失依赖与错误位置 | 所有环境都可用 |
| 仅依公开入口完成指定实验 | 入口、说明、操作与结果的断点 | 初学者一定能够独立完成 |
| 对照规格、测试和轨迹检查解释 | 文档与实现不一致、解释缺少依据 | 仅靠另一个 Agent 就证明正确性 |
| 扮演初学者提出困惑 | 潜在问题与改进假设 | 真实需求、学习效果、满意度或使用意愿 |

公开入口体验宜与实现分离：条件允许时使用独立上下文，先只提供公开入口、任务与成功条件，避免提前告知开发者意图。源码评审、架构评估和解释一致性检查可以直接提供必要的规格、代码与设计背景，无需套用此限制。无法隔离上下文时，如实说明评估条件。Agent 可能用自身知识补足文档缺口；需要额外知识或源码才能完成时，应记录这一事实。必须读源码诊断时，先保留体验阶段证据，再单独记录诊断结论。

操作体验应以实际任务为依据；概念或文档评审可以采用静态检查，但需明确其范围。例如：从 README 开始安装，运行一个指定的已交付实验，改变输入，依据轨迹解释结果，再保存并重放。

以下是正式体验报告的可选记录项，按任务规模选用；快速检查可直接记录在现有任务或 PR 中，无需另建报告：

- 代码基线、环境、Agent／工具条件、任务与可见材料；
- 实际步骤、命令或界面操作、预期与实际结果；
- 首个阻塞位置、恢复尝试、人工提示或额外材料；
- 证据路径、问题影响、建议与尚未验证的判断。

没有 GUI 操作能力时，只能报告 CLI／API／文档体验，不能声称完成 GUI 验证。报告将实际观察与模拟推断分开；修复体验问题后，重跑受影响路径。尚无真实用户反馈时明确写“未开展真实用户验证”，不以 Agent 扮演结果补齐。

## 从实践提炼产品思考（Product Learning from Practice）

每个重要里程碑选择少量影响结果的事件复盘，不为所有操作增加记录负担。可重点观察：

| 实际阻力 | 值得检验的产品假设 |
| --- | --- |
| 反复解释背景或恢复工作困难 | 目标、当前状态、决策理由的保存与检索是否不足 |
| 实现很多却无法收尾 | 完成条件和验证证据是否清晰 |
| 自动修改省事但审查费力 | 变更说明、影响范围与证据组织是否有效 |
| 失败后重复同一策略 | 是否需要更好的诊断、停止条件与策略切换 |
| 人工介入一次便恢复进展 | 介入提供的信息能否转化为工具或交互支持 |
| 多 Agent 引入冲突与返工 | 分工边界与集成成本是否超过收益 |

形成“观察—假设—小幅改变—再次观察”的循环。可按需记录验收结果、人工主动处理时间、介入原因、返工和恢复成本。缺少计时、对照或可比任务时，不宣称效率提升比例，不用 token、代码量或 Agent 数量替代用户收益。

后续有真实使用者时，以小规模任务体验补充证据，观察是否完成实验、是否理解机制、能否迁移到新问题，并区分观察与主观反馈。无需等待全部路线完成，也不把用户招募设为正常工程推进的前置条件。

## 持续执行约定（Ongoing Guidance）

每个里程碑优先留下一个可运行成果；按实际需要补充一个关键协作案例、一次独立 Agent 体验或真实用户反馈。评估以已交付能力为对象，投入与阶段规模匹配。

本文件记录项目定位和后续工作方法，不是功能交付或效果证明。既有 [路线图](../README.md)、[工程约束](../AGENTS.md)、规格与验证要求继续生效。
